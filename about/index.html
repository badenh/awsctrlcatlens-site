    Overview

    The AWS Control Catalog exposes a single control three times when the same behaviour is implemented via Security Hub, AWS Config, and a CloudFormation hook. awsctrlcatlens runs the AWS Control Catalog through a canonicalisation pipeline that groups these cross-executor duplicates into one canonical control, then exposes the three indexes (region, service, framework) that AWS's own API does not expose natively.

    The canonicalisation rule stack is applied in strict order; the first rule that matches wins, subject to any vetoes.

    Disclaimer. The controls listed for any given framework are ONLY those to which a raw control or canonical has been mapped by the AWS Control Catalog — not a statement regarding AWS support for the framework overall, nor the whole official framework.

    Merge rules (R0 – R3)

    RuleNameConditionVetoes
    R0 Force Pairs from a human-curated force list. Used sparingly to encode human-verified groupings the automated rules miss. Bypassed
    R1 Alias Two variants share at least one entry in their Aliases list. Shared aliases are strong evidence from AWS. None
    R2 Normalised exact name Identical normalised control name after stop-prefix strip, stemmer, and paren-abbreviation strip. Exact normalised match trumps everything. None
    R3 Name + common-control Jaccard (Tier A) Token-Jaccard of the normalised names ≥ 0.70 AND common-control-set Jaccard ≥ 0.70. Apply
    R3 Tier B (strong common controls) Token-Jaccard ≥ 0.50 AND common-control-set Jaccard ≥ 0.90 — strong common-control evidence substitutes for weaker name match. Apply

    Vetoes (V1 – V5)

    VetoNameFires when
    V1 Antagonist tokens One variant has a token from an antagonist cluster (global/regional, read/write, inbound/outbound, oidc/saml, …), the other has a different token from the same cluster.
    V2 Trailing-token mismatch Long shared prefix plus distinct tails plus at least one content token in the tail symmetric difference. Catches CIS CloudTrail metric-filter families that would otherwise collapse incorrectly.
    V3 Content-token asymmetry Both variants have unique content tokens (tokens where the service or qualifier vocabulary bypasses the discriminative DF cap).
    V4 Service disjoint Both variants have an inferred AWS service and the intersection is empty under the service-alias table.
    V5 Asymmetric qualifier Either side has a unique token from service, qualifier, antagonist, or digit-token vocabulary.

    Override cycle

    Human-verified decisions live in a curated overrides list. Entries are either force pairs (always merge, R0) or block pairs (never merge, short-circuits every rule). A triage workflow produces a review queue of candidate pairs; applied decisions become new override entries.

    Registry and tombstones

    Canonical ids are stable across refreshes via a persisted id registry. When a canonical's underlying variants disappear from the catalog, its id is tombstoned — permanently reserved so it is never reused for a different concept. Tombstoned canonicals render a minimal page (ARN list and tombstoned-on date) at the same URL they used to live at, so external deep-links stay resolvable.

    The noindex meta on tombstone pages prevents search engines from treating them as current content.

    Executor families

    Raw controls come from four distinct AWS executor surfaces. We tag each variant with its executor family on the raw controls listing and let readers filter by family.

    FamilyResource type~RawBehavior
    Config AWS::Config::ConfigRule 735 Largest family. Reactive detective evaluation against resources after they exist.
    Security Hub AWS::SecurityHub::SecurityControl 575 Curated managed controls. Often wraps a Config rule under the hood but exposes a higher-level identifier.
    CloudFormation Hook AWS::CloudFormation::Type::HOOK 235 Proactive controls. Enforced at stack-create / stack-update time; reject the resource before it is created.
    Organizations AWS::Organizations::Policy::* 70 SCP, RCP, and declarative policies. Enforced at the IAM/API-call boundary across an entire AWS Organization or OU.

    Service inference

    The AWS Control Catalog does not expose a service → controls index. We infer service namespace from GovernedResources[0] of each control's GetControl response — the CloudFormation AWS::<Service>::<ResourceType> format gives us the authoritative service name (e.g. AWS::CloudTrail::Trail → cloudtrail). When GovernedResources is empty (SCPs + root-user controls, ~71 cases), we fall back to parsing the AWS Config rule identifier.

    Service inference is machine-derived from the AWS payload and may still miss edge cases.

    Opt-in regions

    AWS regions are marked opt-in when a new account must explicitly enable them before resources can be deployed; the rest are default-enabled. We fetch this via account:ListRegions and tag opt-in regions with a badge on the regions landing page. The authoritative signal is AWS's own RegionOptStatus field: ENABLED_BY_DEFAULT means default; anything else (DISABLED, ENABLED, ENABLING, DISABLING) means opt-in.

    Framework item repetition

    Every framework page shows a density stat (mapped-rows ÷ unique-canonicals). When density > 1, the same canonical maps to multiple items in that framework. The repetition is real AWS-authored mapping, driven by framework structure:

    PatternExampleMechanism
    Maturity-tiered ACSC Essential Eight ML2 inherits ML1, ML3 inherits ML1 + ML2, so the same canonical appears at every tier.
    Pillar-structured AWS Well-Architected Best practices overlap across pillars (REL / COST / SEC / OPS / PERF / SUS).
    Family-structured CMMC / NIST SP 800-171 One control satisfies requirements in multiple domains (Access Control, Audit, System & Communications Protection).

    Build determinism

    Every page in this site is a deterministic function of a single snapshot of the AWS Control Catalog. Building the site twice from the same snapshot produces byte-identical output; a snapshot.json provenance file at the site root stamps the sealed-at timestamp of the snapshot the build consumed.

    Extension frameworks (Security Hub)

    Two of the frameworks on this site are extension frameworks: the AWS Foundational Security Best Practices and AI Security Best Practices. These are AWS-authored Security Hub standards whose per-standard membership is not published in the Control Catalog's ListControlMappings output — the Control Catalog knows about the member controls (as Security Hub-executed variants) but does not record which standard they belong to. awsctrlcatlens overlays that membership from AWS's own Security Hub user-guide pages so these two standards are first-class citizens of the lens alongside the natively mapped frameworks.

    The join is deterministic. For each standard, awsctrlcatlens parses the dotted Security Hub control ids (such as EC2.8) from the pinned user-guide HTML and matches each one against controls_detailed[arn].Implementation.Identifier on canonicals whose Implementation.Type is AWS::SecurityHub::SecurityControl. Resolved ids become rows carrying source="securityhub-standard" in canonical_framework_items; the native rows carry source="controlcatalog". Both source values flow into the region, service, and crosswalk views at parity — a canonical reached only through an extension-framework overlay contributes to per-region and per-service framework-coverage counts the same way a natively mapped canonical does.

    Misses — Security Hub control ids on the standard's docs page that do not resolve to any Control Catalog canonical — are logged to unresolved.json under the sealed snapshot's extension_frameworks/ directory and surfaced on each extension framework page's methodology section. A non-zero unresolved count is an authentic signal (either a new Security Hub control not yet published in the Control Catalog, or a Security Hub control that has been retired), not an error. The refresh is not failed by non-empty unresolved.json.

    Landing Zone Accelerator Universal Config overlay

    The Landing Zone Accelerator Universal Config page is a third extension framework on this site. The Landing Zone Accelerator on AWS Universal Configuration (LZA UC) is an AWS-authored reference bundle, published on GitHub as aws/lza-universal-configuration, that groups a curated set of AWS Config rule references, Security Hub control suppressions, Security Hub standard activations, and Service Control Policies into a single opinionated configuration for multi-account AWS landing zones. awsctrlcatlens overlays those references onto the AWS Control Catalog's canonical controls so the LZA UC's full control-reference set — mapped and unmapped — can be browsed inside the lens.

    The join uses three paths. (1) Each awsConfig.ruleSets[*].rules[*].identifier entry in security-config.yaml is matched against controls_detailed[arn].Implementation.Identifier on canonicals whose Implementation.Type is AWS::Config::ConfigRule. (2) Each Security Hub control id surfaced by the LZA automation rules (centralSecurityServices.securityHub.automationRules) is matched against Implementation.Identifier on canonicals whose Implementation.Type is AWS::SecurityHub::SecurityControl, reusing the same join machinery as the Phase 6 extension frameworks. (3) Security Hub standard activations (centralSecurityServices.securityHub.standards[*].name) are not joined to canonicals — a standard activation names the standard, not a control, so these rows are preserved as orphans and linked out to the matching native framework page where one exists.

    Orphan rows. LZA references that have no AWS Control Catalog counterpart are kept as rows carrying canonical_id = null, source="lza-uc", and a mandatory orphan_kind discriminator (scp, sh-standard-reference, or unresolved-config-rule) rather than being dropped. The ten Service Control Policy JSONs bundled with the LZA UC are orphan because they are custom AWS-authored JSON policies with no Control Catalog join key — their control content is not catalogued. The two currently unresolvable Config rule identifiers (CODEBUILD_PROJECT_ARTIFACT_ENCRYPTION, INSTANCES_IN_VPC) are orphan because AWS has deprecated the corresponding Config managed rules while the LZA UC still references them; a future AWS Catalog refresh should resolve them automatically. SH-standards references are orphan by construction (standard name, not control id) and link out where the activated standard also exists as a native framework page on this site.

    AWS attribution. AWS authored the LZA UC and all of its referenced configuration; the configuration files, their security control definitions, and all metadata are the intellectual property of Amazon Web Services, Inc. and its affiliates, released under the Apache 2.0 License. awsctrlcatlens's contribution to the LZA UC page is the overlay expression only — the join to Control Catalog canonicals, the per-region deployability on resolved rows, and the orphan-row grouping — none of which is published by the LZA UC directly. The overlay is a derived view; it is neither a substitute for the LZA UC source nor a statement of AWS support for any particular deployment outcome.

    Release-tag pinning. The LZA UC fetcher reads from a pinned release tag (currently v1.3.2) rather than tracking main. The pin is a module-level constant in pipeline/fetch_extension_frameworks.py; bumping it is a deliberate human edit tied to a review of the new tag's security-config surface, not an automated detection. This keeps the overlay stable across daily refreshes and makes the LZA upgrade cycle visible as a single commit in the awsctrlcat repository.

    See the Landing Zone Accelerator Universal Config page for the overlay itself, including the orphan-row section grouped by orphan_kind. The sealed-snapshot artifacts for a given day live under <snapshot>/lza_uc/, which contains the pinned raw security-config.yaml, the ten SCP JSONs, the parsed intermediate (parsed.json), and the orphan-row intermediate (orphans.json).
